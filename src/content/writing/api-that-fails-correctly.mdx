A URL shortener is the "hello world" of backend projects. Store a mapping, return a short code, redirect on lookup. You can write the happy path in about forty lines.

I built one anyway, because the happy path was never the interesting part. Everything that makes an API good — or dangerous — lives in what it does with input it didn't expect and states it didn't plan for.

Source: [github.com/kairugakuo2/url-shortener-minimal](https://github.com/kairugakuo2/url-shortener-minimal). ASP.NET Core Minimal API, EF Core, SQLite.

## The trivial version is a security problem

Here is the naive endpoint, roughly:

```csharp
app.MapPost("/shorten", async (ShortenRequest req, AppDbContext db) =>
{
    var link = new Link { Target = req.Url, Code = GenerateCode() };
    db.Links.Add(link);
    await db.SaveChangesAsync();
    return Results.Ok(link);
});
```

This works. It also does something genuinely dangerous, and it's worth being precise about what.

A URL shortener is, by definition, **a service that takes attacker-controlled input and hands other people a link that your domain vouches for.** That's the whole product. Which means the naive version will happily accept `javascript:` URIs, `file://` paths, and internal addresses like `http://169.254.169.254/` — the cloud metadata endpoint — and then lend your domain's reputation to them.

The last one is the sharp edge. If anything server-side ever follows these URLs — a link preview generator, a health checker, a "verify this link still works" cron job — you have built a server-side request forgery primitive. The attacker submits a link pointing at internal infrastructure, and your server, which sits inside the network perimeter, makes the request on their behalf.

None of that is a bug in the code above. Every line does exactly what it says. The problem is an absent boundary.

## Validation is a boundary, not a nicety

The reframing that made the rest of the design fall out: **validation isn't about helping users avoid typos. It's the line where untrusted data becomes trusted data, and it should be somewhere specific.**

Concretely, an inbound URL has to clear:

- It parses as an absolute URI at all.
- Its scheme is on an allowlist — `http` and `https`, nothing else. Allowlist, never blocklist: you cannot enumerate every dangerous scheme, but you can enumerate the two safe ones.
- Its length is bounded, before it reaches the database.
- Its host isn't a loopback, link-local, or private-range address.

```csharp
static bool IsAcceptableTarget(string candidate, out Uri? uri)
{
    uri = null;
    if (string.IsNullOrWhiteSpace(candidate) || candidate.Length > 2048)
        return false;

    if (!Uri.TryCreate(candidate, UriKind.Absolute, out var parsed))
        return false;

    // Allowlist. A blocklist of dangerous schemes is a list you will
    // always be one entry behind on.
    if (parsed.Scheme != Uri.UriSchemeHttp && parsed.Scheme != Uri.UriSchemeHttps)
        return false;

    uri = parsed;
    return true;
}
```

The important property isn't the specific rules — it's that there is exactly *one* place where a string becomes a URL this service is willing to act on. Validation scattered across handlers is validation that will be inconsistent, and inconsistent validation is the same as none: an attacker only needs the one path that skipped a check.

## Failures should be machine-readable

The second decision was that errors get a schema, same as successes.

APIs tend to fail in prose. A 400 with `"Invalid request"` in a string field, a 404 with an HTML error page, a 500 with a stack trace in development and an empty body in production. Every one of those is a different shape, so every client ends up with bespoke parsing per endpoint, and most clients give up and just check the status code.

ASP.NET Core has [RFC 7807 ProblemDetails](https://datatracker.ietf.org/doc/html/rfc7807) built in, which standardizes the shape:

```json
{
  "type": "https://tools.ietf.org/html/rfc7231#section-6.5.1",
  "title": "One or more validation errors occurred.",
  "status": 400,
  "detail": "Target URL must use http or https.",
  "instance": "/shorten"
}
```

Same envelope for a 400, a 404, and a 500. A client writes one error handler instead of six.

Getting this consistent meant moving error handling out of individual endpoints entirely. When each handler formats its own errors, they drift — one returns a bare string, another a wrapped object, a third throws and gets whatever the framework's default is. Centralized:

```csharp
app.UseExceptionHandler(handler =>
{
    handler.Run(async context =>
    {
        var feature = context.Features.Get<IExceptionHandlerFeature>();

        var (status, detail) = feature?.Error switch
        {
            LinkNotFoundException => (StatusCodes.Status404NotFound, "No link with that code."),
            ValidationException v => (StatusCodes.Status400BadRequest, v.Message),
            // Unrecognized exceptions: generic message only. Internal
            // details go to logs, never to the client.
            _ => (StatusCodes.Status500InternalServerError, "An unexpected error occurred."),
        };

        await Results.Problem(statusCode: status, detail: detail)
                     .ExecuteAsync(context);
    });
});
```

That last branch is a security decision wearing engineering clothes. Verbose errors are a reconnaissance gift: stack traces disclose framework versions and file paths, database exceptions disclose schema, and a login that says "user not found" versus "wrong password" discloses which accounts exist. The rule I settled on — **detailed to the logs, generic to the client** — is the least interesting-sounding sentence here and probably the most valuable.

## Status codes carry meaning

`200` for everything, with a `success: false` field, is a common pattern and a bad one. It discards a layer of the protocol that every proxy, cache, and monitoring tool already understands, and forces every consumer to parse a body to learn whether the call worked.

What each code actually commits to:

| Code | Means | Should the client retry? |
|---|---|---|
| `201 Created` | Resource exists now; `Location` header points at it | — |
| `301` / `302` | The redirect itself. Permanent is cacheable — which also means uncorrectable | — |
| `400 Bad Request` | Malformed. Don't send this again | No |
| `404 Not Found` | No such code | No |
| `409 Conflict` | Custom alias already taken | No, choose another |
| `500 Internal Server Error` | Our fault | Yes, with backoff |

The retry column is the one that matters operationally. A client can build correct behavior — back off on 5xx, surface 4xx to the user, don't hammer — purely from the status code, without understanding anything about URL shortening.

The redirect choice has a subtlety worth flagging: `301` is permanent and aggressively cached by browsers, so a mistyped target is effectively unfixable for anyone who already followed it. `302` keeps control on the server at the cost of a request per hit. I chose `302` — for a service where links are user-generated and therefore sometimes wrong, keeping the ability to correct them was worth more than the caching.

## Health checks and startup

Two endpoints that exist purely for operations:

```csharp
builder.Services.AddHealthChecks()
       .AddDbContextCheck<AppDbContext>();

app.MapHealthChecks("/health");
```

The distinction that matters: **liveness** ("is the process running?") versus **readiness** ("can it actually serve traffic?"). A service that has started but can't reach its database is alive and not ready. Conflating them means an orchestrator either restarts a healthy process or routes traffic to one that can only return 500s.

Seeding routines came from a smaller annoyance — a fresh clone should run. If setup requires undocumented manual steps, the documentation is wrong, and the first person to discover that will be me in six months.

## What the tests are actually for

The xUnit suite mostly doesn't test that shortening a URL works. That path runs on every manual check.

It tests:

- Each rejected scheme is actually rejected — `javascript:`, `data:`, `file:`, protocol-relative `//evil.com`.
- Over-length input is rejected before it touches the database.
- An unknown code returns 404 with a ProblemDetails body, not an HTML page.
- A duplicate custom alias returns 409, not 500.
- Unhandled exceptions produce a generic message with nothing internal in the body.

Every one is a failure path. That's the point: **the happy path is self-testing because you exercise it constantly; the error paths only run when something is already going wrong.** Those are the ones that need automation.

Docker and GitHub Actions exist for a narrower reason than "best practice." Containerization means the thing I tested is the thing that runs — no "works on my machine" gap between my SDK version and the deployment target. CI means the failure-path tests run on every push, including the pushes where I'm confident the change is trivial. Those are exactly the pushes where I would otherwise skip them.

## What I'd do differently

**Rate limiting isn't optional for this shape of service.** An unauthenticated endpoint that writes to a database is a free write primitive for anyone who finds it. ASP.NET Core 7+ ships `AddRateLimiter`; there's no good reason I didn't wire it up from the start.

**SQLite was the right call and won't stay that way.** It's a single writer. Fine at my scale, a hard ceiling at any real one. Knowing which constraint you've accepted matters more than avoiding constraints.

**Click tracking writes on the read path.** Every redirect does a synchronous database write before responding, which puts a write in the latency path of the operation that most needs to be fast. Buffering in memory and flushing periodically trades exact counts for latency — and for analytics, approximate counts are almost always fine.

The general lesson is the one I started with: the trivial version of a problem is trivial only if you ignore what happens when the input is hostile or the dependency is down. That's most of the actual work, and it's where the interesting design decisions live.
