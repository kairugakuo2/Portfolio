Every service that talks to another service has to answer one question first: *why should I believe you are who you say you are?*

The honest answer, almost always, is "because you hold a secret only the real one would hold." Which pushes the problem back a step. How did you get the secret? And what happens when it needs to change?

This is the key management problem, and it is much less about cryptography than people expect. The math is settled. What isn't settled is the operational choreography around it: distribution, rotation, revocation, and — the part that actually bites — what the system does when a piece of that choreography is unavailable.

What follows is how the problem class works generally. It is not a description of any particular employer's system.

## Why the secret can't just be in the config file

The default move is to put a key in a config file, an environment variable, or a deployment secret, and move on. This works, in the sense that the service starts. It fails in four specific ways.

**It never changes.** A key in a config file has no lifecycle. In practice it lives as long as the service does, which in enterprise software means years. Every day it exists is another day of accumulated exposure — in backups, in CI logs, in the terminal history of whoever deployed it, in the Slack message where someone pasted it to debug a staging issue at 11pm.

**Its blast radius is the whole fleet.** If every instance shares one key, compromising one host compromises the identity of all of them. There is no way to answer "which machine leaked this?" because the key carries no information about which machine held it.

**Rotation requires a human.** Changing it means someone touches production, coordinates a restart, and hopefully updates every consumer. Anything requiring a human at 3am is a thing that will not happen at 3am.

**It's indistinguishable from a valid attacker.** A stolen config key is a *perfectly valid* credential. Nothing in the protocol can tell the difference between the real service and someone who read a `.env` file.

Zero-trust architecture takes the position that the network is already hostile and location proves nothing — being inside the datacenter earns you no credit. Identity has to be proven cryptographically, per request, with credentials that are short-lived and attributable to a specific workload.

Which is a fine principle. It just relocates the hard part.

## The bootstrap problem

Here is the recursion. To get a credential from the issuing authority, you must authenticate to the issuing authority. To authenticate, you need a credential. To get a credential…

This is the bootstrap problem, and it cannot be solved by cryptography alone. Somewhere the chain has to terminate in something the platform can vouch for that isn't itself a distributed secret. In practice that anchor is one of:

- **Hardware.** A TPM or secure enclave holds a key burned in at manufacture. The strongest anchor — extraction requires physical possession and meaningful effort.
- **Platform attestation.** The cloud provider or orchestrator signs a statement about what this workload is. Kubernetes projected service account tokens and cloud instance identity documents both work this way. The trust root is the platform's own control plane.
- **OS-level protection.** The operating system encrypts data such that only a specific machine or user account can decrypt it, keeping the key material outside the application's reach. Windows DPAPI is the canonical example.
- **An operator, exactly once.** A human installs an initial credential at provisioning time, and that credential's only job is to obtain better, shorter-lived ones. This is the weakest link in the list, which is why its lifetime should be measured in minutes.

The shape is always the same:

<div class="diagram">{`
   ┌──────────────┐   1. attest ("I am workload X,     ┌───────────────┐
   │              │      here is proof")               │               │
   │   Workload   │ ─────────────────────────────────► │   Registrar   │
   │              │                                    │  (issuing     │
   │              │ ◄───────────────────────────────── │   authority)  │
   └──────┬───────┘   2. short-lived signing key       └───────────────┘
          │
          │ 3. encrypt at rest, scoped to this host
          ▼
   ┌──────────────┐
   │  Local cache │   ← survives restarts, not exfiltration
   └──────────────┘
`}</div>

The workload proves something about itself that it cannot forge, receives a credential it *can* use, and caches it locally so a registrar hiccup doesn't take down the service.

That local cache is where a lot of designs get sloppy. It exists for availability, so people treat it as a convenience and store it carelessly. But a cached signing key on disk is a signing key on disk. It needs encryption bound to the host, filesystem ACLs restricting it to the service account, and a hard lifetime after which it is refused even if it decrypts successfully. I wrote about the at-rest side of this [separately](/writing/secrets-at-rest).

## Rotation, and why it can't be a swap

Once a workload has a key, that key needs to be replaced periodically — because keys leak, because compliance regimes mandate maximum lifetimes, and because a rotation path that is never exercised is a rotation path that does not work. If you only rotate during an incident, you are debugging your rotation logic during an incident.

The naive implementation is a swap: generate a new key, replace the old one, done.

This breaks immediately in any distributed system, for a reason that has nothing to do with cryptography. **There is no instant at which all participants agree the switch happened.**

Consider a signer and a verifier. The signer rotates to key B. In the window before the verifier learns about key B:

<div class="diagram">{`
  t0 ──────────── t1 ──────────── t2 ──────────── t3
  │               │               │               │
  │  signer: A    │  signer: B    │  signer: B    │  signer: B
  │  verifier: A  │  verifier: A  │  verifier: A  │  verifier: B
  │               │               │               │
  │      ok       │  ✗ REJECTED   │  ✗ REJECTED   │      ok
                  └───────────────────────────────┘
                        the failure window
`}</div>

Everything signed in that window is rejected as forged. Not degraded — *rejected*, as an authentication failure, which is exactly the alarm that wakes people up.

And the window is never zero. Propagation takes time. Caches have TTLs. Some verifier is mid-request with the old key already fetched. Some replica was network-partitioned for four seconds. Clock skew means participants don't even agree on *when* t1 was.

## Dual-key grace periods

The fix is to stop thinking of rotation as a swap and start thinking of it as a **fade**. During rotation there is no single valid key; there is a set.

<div class="diagram">{`
  phase 1: STEADY        sign: A          accept: {A}
  phase 2: PREPARED      sign: A          accept: {A, B}    ← B distributed
  phase 3: CUTOVER       sign: B          accept: {A, B}    ← grace period
  phase 4: RETIRED       sign: B          accept: {B}       ← A revoked
`}</div>

The critical ordering is that **the new key becomes acceptable before it becomes used**, and the old key stays acceptable for a bounded window after it stops being used. Verifiers are prepared to accept B while signers are still producing A; once every verifier is known to have B, signers cut over; only after the grace period expires is A retired.

This has a cost worth stating plainly. During phases 2 and 3, a compromised old key is still valid. The grace period is a deliberate, bounded increase in exposure, traded for not having an outage. That trade is the right one, but it should be a decision, not an accident — which means the grace period should be as short as your propagation guarantees allow, and no shorter.

How short is that? It's bounded below by the worst-case time for a new key to reach every verifier: cache TTL, plus propagation delay, plus a margin for clock skew, plus however long your longest-running in-flight request can be. Setting it to "an hour" because an hour sounds safe is how you end up with either mystery auth failures or a much wider exposure window than you meant.

The retirement step matters as much as the introduction. A grace period that never ends is just a system with two permanent keys, and a rotation scheme that accumulates valid keys forever has made things worse than the config file it replaced.

## When the registrar is down

Now the part that separates a design that works from one that works on the happy path.

The registrar is a dependency. Dependencies fail. If every workload needs the registrar to function, you have built a distributed system with a single point of failure and added cryptography to it.

The question a design has to answer is: **what does a workload do when it cannot reach the authority that issues its identity?**

There are exactly three options, and the choice is a security decision, not an engineering one.

**Fail closed.** Refuse to operate. Correct for the highest-sensitivity operations — you do not want a payment authorization service continuing on an identity it cannot confirm. But applied everywhere, a registrar outage becomes a total outage, and you have made availability strictly worse than the config-file design.

**Fail open.** Continue without verification. Almost never acceptable. This converts a registrar outage into an authentication bypass, which is a strictly worse incident than downtime, and an attacker who can cause the outage now controls the security boundary.

**Degrade gracefully.** Continue on the cached credential, within limits that were decided in advance:

- Serve from the cache while it's within its lifetime, even if it can't be refreshed.
- Keep retrying with exponential backoff and jitter — so the whole fleet doesn't stampede the registrar the instant it recovers and immediately knock it back down.
- Emit loud, escalating alerts. Degraded mode is an incident, not a resting state.
- Enforce a hard ceiling. Past some multiple of normal lifetime, refuse — even though the cached key still cryptographically validates. A key that cannot be revoked because the revocation channel is down is a key you should stop trusting eventually.
- Consider narrowing scope while degraded: continue serving reads on a cached identity, refuse privileged writes.

That last point is the interesting one. Degradation doesn't have to be binary. The useful question isn't "up or down?" but "which operations remain safe when I can no longer confirm my identity is current?"

Fail-closed and fail-open are both easy to implement and both wrong for most systems. The engineering is in defining the middle: how long, under what constraints, with what alerting, and which operations get cut first.

## Testing the parts that only happen during failures

Rotation logic is uniquely hard to test because its interesting behavior only occurs during transitions and outages — states that are rare in production and easy to skip in tests.

The cases worth explicit coverage:

- **Cryptographic round-trip.** Encrypt, restart the process, decrypt. Catches the classic bug where key material is bound to something process-local and silently doesn't survive a restart.
- **Both sides of the grace window.** A signature made with the old key just inside the grace period must verify. One made just outside must not. Off-by-one here is a real outage.
- **Registrar unreachable at cold start.** No cache, no registrar. The system should fail cleanly with a diagnosable error — not a null reference three layers down.
- **Registrar unreachable with a warm cache.** Should degrade, not fail.
- **Registrar returns garbage.** A 500, a truncated response, an expired key, a valid response for the wrong workload. "Down" is the easy failure; "up and wrong" is the one that produces weird bugs.
- **Interrupted rotation.** Kill the process mid-rotation. On restart it should reach a consistent state, not a half-written cache that decrypts to nothing.
- **Clock skew.** Move the clock. Validity windows are wall-clock comparisons, and wall clocks are wrong more often than people assume.

The failure-path tests are the ones with real value. The happy path gets exercised constantly in every environment. The registrar-outage path gets exercised once, in production, at the worst possible time — unless you exercise it in CI.

## What I'd keep

Three things generalize past key management:

**Distribution has no instants.** Any design that assumes all participants transition simultaneously is broken; you just haven't seen it yet. Overlap windows are not a workaround, they're the correct model.

**Availability decisions during a security dependency outage are security decisions.** "What happens when the auth service is down" gets answered by default — by a timeout, a retry loop, a null check someone wrote without thinking about it. Answer it deliberately or it gets answered for you.

**Anything requiring a human under pressure is a design defect.** Manual rotation isn't a process, it's a scheduled incident.
