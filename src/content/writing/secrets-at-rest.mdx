A service that caches a credential locally has a problem the distributed design didn't have: there is now a secret sitting on a disk, and it needs to survive a restart without surviving an exfiltration.

This is a narrower problem than key distribution — one host, one file — and the constraints are unusually concrete. It's also where a lot of otherwise careful systems get careless, because the cache exists for availability and gets treated as an implementation detail rather than what it is: a signing key on disk.

Below is how the problem class works generally. It describes no particular employer's implementation.

## The recursion, again

To protect a secret at rest you encrypt it. To encrypt it you need a key. That key also has to live somewhere.

Storing the encryption key next to the ciphertext is theater — it raises the attacker's effort from `cat` to `cat` plus one function call. The recursion has to bottom out in something that isn't a file your process can read.

On a single host the realistic options:

- **Hardware (TPM).** Key material is generated in and never leaves the chip. Strongest available, and the least portable.
- **OS-managed key derivation.** The operating system derives a key from user or machine credentials and never exposes it. Windows DPAPI, macOS Keychain, Linux kernel keyrings.
- **An external secret manager.** Push the problem to a network service — which reintroduces the network dependency the local cache existed to avoid.

The OS route is usually the pragmatic answer for a cached credential, because it needs no additional infrastructure and binds decryption to the machine.

## What DPAPI actually does

Windows DPAPI (Data Protection API) is a pair of calls, `CryptProtectData` and `CryptUnprotectData`, exposed in .NET as `ProtectedData`:

```csharp
byte[] Protect(byte[] plaintext, byte[] entropy) =>
    ProtectedData.Protect(plaintext, entropy, DataProtectionScope.CurrentUser);

byte[] Unprotect(byte[] ciphertext, byte[] entropy) =>
    ProtectedData.Unprotect(ciphertext, entropy, DataProtectionScope.CurrentUser);
```

The key is derived by the OS from the user account's credentials (or the machine key, for `LocalMachine` scope). Your process never sees it and cannot export it.

The `entropy` parameter is secondary entropy — an application-supplied value mixed into the derivation, so that ciphertext protected by your application can't be decrypted by *another* application running as the same user. Without it, `CurrentUser` scope means any process in the user's session can call `Unprotect` on your file. It's frequently omitted, and omitting it discards most of the isolation.

The scope choice is the real decision:

| Scope | Decryptable by | Use when |
|---|---|---|
| `CurrentUser` | That Windows account, on that machine | The service runs under a dedicated account |
| `LocalMachine` | **Any process on the machine** | Rarely — it's much weaker than it sounds |

`LocalMachine` is the tempting one because it survives account changes and works for services running as `LocalSystem`. It also means any local process, at any privilege level, can decrypt your key cache. That's typically the wrong trade.

## Be precise about the threat model

DPAPI, keychains, and keyrings all defend against a specific and limited threat: **offline access to the file.**

If someone steals the disk, restores your backup, or copies the file to another machine, they get ciphertext they cannot decrypt, because the derivation is bound to a machine and account they don't have.

What it does **not** defend against:

- **Code running as the same user on the same machine.** It can simply call `Unprotect`. This is by design — that's the entire mechanism.
- **An attacker with administrator or SYSTEM.** They can impersonate the account, read process memory, or attach a debugger.
- **Memory disclosure.** The plaintext exists in RAM while in use.

So encryption at rest raises the bar from "read the file" to "execute code as this account on this host." That's a real improvement and it is not a security boundary against local code execution. Systems that treat it as one are surprised later.

Which is why the filesystem ACL matters as much as the encryption:

```
key.cache
  OWNER:  svc-account
  ACL:    svc-account  : Read, Write
          Administrators: Full
          (no inherited permissions, no Users, no Everyone)
```

Inheritance disabled deliberately — a cache file that inherits a permissive parent directory ACL is readable by accounts nobody intended. The two controls cover different attackers: ACLs stop other local accounts, DPAPI stops offline access. Either alone leaves a gap.

## SecureString doesn't do what the name implies

.NET's `SecureString` stores a string encrypted in memory and offers `Dispose` for deterministic clearing. It exists because ordinary .NET strings are immutable, garbage-collected, and relocatable — you cannot reliably zero one, and copies may persist until collection, including in a crash dump or page file.

The problem: **to use a secret, you must decrypt it.** Every consuming API needs a plain `string` or `byte[]`, so the value is unprotected in managed memory during use, and at that moment it has all the properties `SecureString` was meant to avoid.

Microsoft's own documentation now discourages it for new development, and it is not fully implemented outside Windows. On Linux and macOS, .NET Core's `SecureString` provides no encryption at all — it's a plain buffer with a reassuring type name. Code that reads as hardened is, on those platforms, doing nothing.

The realistic guidance:

- Prefer `byte[]` you clear explicitly with `CryptographicOperations.ZeroMemory` in a `finally`.
- Minimize the window: decrypt immediately before use, clear immediately after.
- Don't convert to `string` — you lose control of the lifetime the moment you do.

```csharp
byte[] key = Unprotect(ciphertext, entropy);
try
{
    Sign(payload, key);
}
finally
{
    CryptographicOperations.ZeroMemory(key);
}
```

This is *better hygiene*, not a guarantee. A managed runtime can move buffers, the OS can page memory to disk, and a crash dump can capture everything. The goal is reducing exposure window and blast radius, not eliminating them — and being clear-eyed about which one you achieved.

## The operational details that get skipped

**Cache entries need their own expiry.** A cached credential that decrypts successfully is not necessarily still valid. Store the issuance and expiry timestamps alongside it and check them on load — otherwise a host that's been offline for a month happily resumes with a long-dead key.

**Writes must be atomic.** Write to a temp file, fsync, then rename. A process killed mid-write otherwise leaves a truncated cache that decrypts to garbage, and the error surfaces as a cryptographic failure rather than a corrupt-file error — sending you to debug the wrong subsystem entirely.

**Failed decryption is expected, not exceptional.** It happens legitimately: the machine was reimaged, the service account's password was reset (which can invalidate DPAPI-derived keys), the file was restored from another host. The correct response is discard the cache and re-bootstrap, with a warning. Crashing on startup because a *cache* couldn't be read is a self-inflicted outage.

**Never log the plaintext.** Obvious, and it still happens — usually via a debug log statement that serializes a whole config object, or an exception handler that dumps state. Give secret-bearing types a `ToString()` that returns `"[redacted]"`. Assume every object will eventually be logged by someone debugging at 2am, because it will be.

## The summary

Encryption at rest on a single host is a bounded, achievable goal: make the file useless to anyone who obtains it without the machine. It is not, and cannot be, protection against code running as your service account.

Most of the value is in the unglamorous parts — the ACL, the atomic write, the expiry check, the `ToString()` override. The cryptography is one function call. The engineering is everything around it.
